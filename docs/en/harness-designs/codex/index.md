# Breaking Down Codex's Harness Design

OpenAI's [Codex](https://openai.com/index/harness-engineering/) is arguably the product most tied to harness fundamentals: the article that named the field, Harness Engineering, summarized the OpenAI team's experience building a product with Codex.

In one sentence: **the repository is the system of record, AGENTS.md is only a directory page, and engineering value lies in designing environments, expressing intent, and building feedback loops.**

## Background

The OpenAI team used Codex to deliver a product that grew to more than a million lines of code in a matter of weeks, and **every line of code was written by Codex** (see "Designing for growth" in [Harness Engineering](https://openai.com/index/harness-engineering/)). Codex CLI itself is an open-source monolithic binary implemented in Rust ([github.com/openai/codex](https://github.com/openai/codex)), but its main contribution lies in **conventions** and **context engineering**, not extension points.

## Instruction Subsystem: AGENTS.md Is a Directory Page, Not an Encyclopedia

This is Codex's most influential contribution to harness theory:

> A single giant instruction file is difficult to check mechanically for coverage, freshness, ownership, and cross-links, so drift is inevitable. We therefore stopped treating AGENTS.md as an encyclopedia and began treating it as a **directory page**. Codebase knowledge lives in structured documentation, and AGENTS.md points to it.

(A paraphrase of the "AGENTS.md should be a directory page" section in [Harness Engineering](https://openai.com/index/harness-engineering/).)

Lecture 4 says "one giant instruction file fails," and Codex's answer is to keep AGENTS.md to roughly 100 lines, move content into `docs/` as it approaches the limit, and let the agent read files on demand: "give the map, not the manual."

The accompanying principle is to **enforce invariants, not micromanage implementation**. AGENTS.md should contain only inviolable constraints and verification commands, leaving implementation details to the model. This maps to Lecture 2's "constraints rather than micromanagement."

## Context Subsystem: Write-Select-Compress-Isolate

Codex's context engineering reduces to four strategies, a community framework mapped back onto Codex (see [Context Engineering for Codex CLI](https://codex.danielvaughan.com/2026/06/10/context-engineering-codex-cli-write-select-compress-isolate-june-2026/)):

- **Write**: Persist context outside the window: conclusions go into documentation and state into files, not the conversation.
- **Select**: Pull only necessary tokens into the window. AGENTS.md points the way and files are read on demand.
- **Compress**: Codex supports automatic compaction and manual `/compact`, with a customizable `compact_prompt`.
- **Isolate**: Subagents isolate the context of different tasks, so a frontend subagent never sees the backend database schema.

Community source analysis in [codex-harness-internals](https://github.com/AlexKenbo/codex-harness-internals) shows that `build_environment_update_item` outputs only **changed fields** (CWD, git branch, file system) when the environment changes, rather than repeating the full system context every turn.

## Tools and Boundaries: Worktree Isolation + Subagents

**1. Environment isolation with git worktrees.** The "Environment" section of [Harness Engineering](https://openai.com/index/harness-engineering/) states that every task runs in an independent git worktree, paired with a local observability stack (logs, metrics, and traces), so every change can be verified in isolation. This is Lecture 7's task boundary enforced by the environment, not requested through instructions.

**2. Core-level subagents.** Codex's `spawn_agent` / `wait_agent` are core tools: the model creates a subagent, gives it independent session history and a tool set, and waits for the result. Subagents inherit AGENTS.md instructions from their parent but run in **their own context**. Configuration lives in `.codex/agents/*.toml`, where different models and instructions can be specified (see the Sub-agents section of [Context Engineering for Codex CLI](https://codex.danielvaughan.com/2026/06/10/context-engineering-codex-cli-write-select-compress-isolate-june-2026/)). Each subagent is a work unit with clear boundaries, in the spirit of Lecture 12's handoffs.

## Feedback Subsystem: Put Verification Commands in the Specification

OpenAI's practice lists verification commands explicitly in AGENTS.md, making "how to confirm the work is correct" part of the repository. Tests, CI, documentation, and observability configuration are all generated by Codex, each providing an executable verification path. The answer to a powerful but unreliable model is to make **verification paths a default component of the harness**.

Approval policies and plan mode provide feedback in the other direction: before high-risk operations execute, the system produces a plan and requests approval, turning task boundaries and human decision-making authority into runtime controls.

## Mapping to the Course Framework

| Subsystem | Codex's Implementation | Assessment |
| --- | --- | --- |
| Instructions | AGENTS.md directory page + split docs/ + enforced invariants | Textbook-quality; defines "give the map, not the manual" |
| Tools | Worktree isolation + spawn_agent subagents | Strong boundaries enforced through environment isolation |
| Environment | Independent worktrees + observability stack | Worktree isolation is its signature feature |
| State | Write strategy (state written to files/documentation) | Relies on conventions rather than built-in memory |
| Feedback | Verification commands in the specification + approval policies + plan mode | Makes feedback paths the default; worth adopting |

Codex works by "subtraction": it keeps the core restrained and places more responsibility on repository conventions and context engineering. This is why the community says "Codex's harness philosophy is more valuable than its code."

## Designs Worth Adopting

1. **Write AGENTS.md as a directory page**: Keep it to roughly 100 lines, point to details in docs/, and make it mechanically checkable.
2. **Specify only invariants**: Hard constraints plus verification commands, with the rest left to the model.
3. **Use worktrees for environment isolation**: Enforce task boundaries through the environment, not through pleas in instructions.
4. **Send only environment-context deltas**: Output only changed fields each turn instead of repeating the full system context.
5. **Use subagents for context isolation**: Split the context along with the task so subtasks do not pollute the main loop.
